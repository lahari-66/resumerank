# ResumeRank – Shared Interfaces

Agreed in Day 1, Hour 1. These three interfaces are the only contract between the
processing pipeline (Member A) and the API / frontend (Member B). **Neither side changes
anything here without the other's agreement.** Attribute names are copied from blueprint
section 11 – do not retype or rename them.

Region for every resource: **ap-south-1 (Mumbai)**, except the billing alarm (us-east-1,
where AWS publishes billing metrics).

## 0. Resource names

Bucket names are globally unique across all AWS accounts, so the blueprint names
`resumerank-site` / `resumerank-resumes` get a short team suffix. Code never hard-codes
any of these – they are read from Lambda environment variables (and from the gitignored
`.env` / `frontend/config.js` for local tooling).

| Resource | Name | Notes |
| --- | --- | --- |
| Website bucket | `resumerank-site-<suffix>` | static website hosting (Day 1, Hr 6) |
| Resumes bucket | `resumerank-resumes-<suffix>` | private, Block Public Access ON, 7-day lifecycle on `resumes/` |
| Jobs table | `Jobs` | on-demand |
| Candidates table | `Candidates` | on-demand, GSI `ScoreIndex` |
| SNS topic | `resumerank-alerts` | standard topic, email subscriptions for both members |
| Upload queue | `resumerank-queue` | SQS standard, visibility timeout 12 min, redrive to the DLQ after 3 receives |
| Dead-letter queue | `resumerank-dlq` | SQS standard, 14-day retention |
| Processor Lambda | `process_resume` | Python 3.12, 256 MB, 120 s; SQS trigger: batch size 1, maximum concurrency 5, report batch item failures |
| API Lambda | `api_handler` | Python 3.12, 256 MB, 10 s |
| Processor role | `role-processor` | blueprint section 14 |
| API role | `role-api` | blueprint section 14 |
| Custom metric | namespace `ResumeRank`, name `CandidateScore` | no dimensions – a per-job dimension would create one billable metric per job (free tier: 10) |

## 1. S3 key convention

```
resumes/{jobId}/{candidateId}.pdf
```

- `jobId` and `candidateId` are lower-case UUID4 strings generated by `api_handler`.
- `api_handler` is the only writer of keys (through the pre-signed PUT URL).
- The resumes bucket sends **ObjectCreated:Put** (prefix `resumes/`, suffix `.pdf`) to the SQS
  queue `resumerank-queue`; `process_resume` consumes the queue (each message body is the S3
  event JSON) and parses the key by splitting on `/`. Keys arrive URL-encoded in the S3 event and must
  be `unquote_plus`-decoded before parsing.
- Anything that does not match the pattern is logged and ignored (no FAILED write, since
  there is no candidate to attach it to).
- Permanent problems (unknown job, unreadable PDF) mark the candidate FAILED and the message is
  deleted. Transient problems (DynamoDB unavailable) and malformed messages are reported as
  batch item failures, retried by SQS and moved to `resumerank-dlq` after 3 receives.

## 2. DynamoDB schemas

### Table `Jobs`

| Attribute | Type | Description |
| --- | --- | --- |
| `jobId` (PK) | String | UUID generated by `api_handler` |
| `title` | String | e.g. "Backend Developer Intern" |
| `requiredSkills` | String set | lower-cased canonical skill names, e.g. `{"python","aws","sql","docker"}`; never empty |
| `minYears` | Number | minimum experience (0 for fresher roles) |
| `recruiterEmail` | String | recruiter contact (see note on SNS below) |
| `createdAt` | String | ISO-8601 UTC timestamp |
| `description` | String | optional job description text (≤ 5,000 characters) |

### Table `Candidates`

| Attribute | Type | Written by | Description |
| --- | --- | --- | --- |
| `jobId` (PK) | String | API | groups all candidates of one job |
| `candidateId` (SK) | String | API | UUID per upload |
| `name` | String | API | from the upload form (file name for bulk uploads) |
| `email` | String | API | from the upload form; absent for recruiter bulk uploads |
| `status` | String | API → processor | `PENDING` → `SCORED` \| `FAILED` |
| `score` | Number | API (0) → processor | 0–100 composite score; **GSI sort key** |
| `skillScore`, `expScore`, `eduScore` | Number | processor | component scores |
| `matchedSkills`, `missingSkills` | List of String | processor | shown on the leaderboard |
| `yearsExperience` | Number | processor | estimated, capped at 15 |
| `textPreview` | String | processor | first 300 characters of OCR text |
| `s3Key` | String | API | `resumes/{jobId}/{candidateId}.pdf` |
| `processedAt` | String | processor | ISO-8601 UTC |
| `createdAt` | String | API | ISO-8601 UTC (upload requested) |
| `failureReason` | String | processor | only when `status = FAILED` |
| `decision` | String | API (recruiter) | `SHORTLISTED` \| `REJECTED` \| `NONE`; absent means `NONE` |
| `decidedAt` | String | API (recruiter) | ISO-8601 UTC |

### GSI `ScoreIndex`

- Partition key `jobId` (String), sort key `score` (Number), projection **ALL**.
- Leaderboard query: `KeyConditionExpression jobId = :j`, `ScanIndexForward=False`.

> **Clarification (needs both members' OK):** a GSI only contains items that have the sort
> key. If PENDING items had no `score`, the leaderboard would never show PENDING or FAILED
> candidates. So `api_handler` writes `score = 0` on the PENDING item, the processor
> overwrites it on SCORED, and FAILED keeps `score = 0`. The frontend shows "–" instead of a
> number whenever `status != SCORED`.
>
> `failureReason` and `createdAt` on Candidates are additions to blueprint section 11
> (T1.6 asks for "FAILED written with reason"; there was no attribute named for it).

### Processor write rules

- Uses `UpdateItem` (never `PutItem`) keyed on `jobId` + `candidateId`, so a repeated event
  is idempotent and never wipes `name` / `email`.
- Numbers go through `Decimal` (boto3 rejects `float`).

## 3. API contract

HTTP API (API Gateway v2), Lambda proxy integration (payload format 2.0), all routes
handled by `api_handler`. All bodies are JSON. Errors are always:

```json
{ "error": "human-readable message" }
```

with status `400` (validation), `401` (recruiter key missing/wrong), `404` (unknown job or
candidate), `429` (API Gateway throttling) or `500` (unexpected).

| Route | Access | Purpose |
| --- | --- | --- |
| `GET /jobs` | public | all jobs with applicant counts, or one job with `?jobId=` |
| `POST /upload-url` | public | PENDING candidate + pre-signed PUT URL |
| `GET /status?jobId=&candidateId=` | public | a candidate's own result |
| `POST /skills/extract` | public | skills found in a job description |
| `POST /jobs` | recruiter | create a job |
| `GET /candidates?jobId=` | recruiter | ranked leaderboard |
| `POST /decision` | recruiter | shortlist / reject / clear |
| `GET /resume-url?jobId=&candidateId=` | recruiter | 5-minute pre-signed GET URL to view the PDF |

**Recruiter access:** recruiter routes require the header `x-recruiter-key` to equal the
`RECRUITER_KEY` environment variable of `api_handler` (compared in constant time). The key is
entered once on the recruiter page and kept in the browser's session storage. This is a simple
shared secret, not user accounts – Cognito sign-in is future work.

API Gateway throttling on the `$default` stage: rate 20 requests/s, burst 50.

### `POST /jobs`

Request:

```json
{
  "title": "Cloud Engineer Intern",
  "requiredSkills": ["python", "aws", "docker", "linux", "sql"],
  "minYears": 0,
  "recruiterEmail": "recruiter@example.com"
}
```

Rules: `title` non-empty; `requiredSkills` a non-empty list, trimmed + lower-cased +
de-duplicated; `minYears` integer 0–15; `recruiterEmail` contains `@`.

Response `201`:

```json
{
  "jobId": "3f1c2a7e-5b8d-4c1e-9a0f-2d6b7e8c9a10",
  "title": "Cloud Engineer Intern",
  "requiredSkills": ["aws", "docker", "linux", "python", "sql"],
  "minYears": 0,
  "recruiterEmail": "recruiter@example.com",
  "createdAt": "2026-10-13T09:15:02Z"
}
```

### `POST /upload-url`

Request:

```json
{
  "jobId": "3f1c2a7e-5b8d-4c1e-9a0f-2d6b7e8c9a10",
  "name": "Test Candidate One",
  "email": "r1@example.com",
  "contentType": "application/pdf",
  "fileSize": 184321
}
```

Rules: `email` is optional (recruiter bulk uploads have none); job must exist (`404` otherwise); `contentType` must be `application/pdf`;
`fileSize` 1 – 5,242,880 bytes. The API writes the PENDING Candidates item, then signs a
PUT for exactly `resumes/{jobId}/{candidateId}.pdf`, valid 300 s, with `ContentType` and
`ContentLength` bound into the signature.

Response `200`:

```json
{
  "candidateId": "a9e4d1b2-7c3f-4e5a-8b6d-0f1e2d3c4b5a",
  "s3Key": "resumes/3f1c2a7e-5b8d-4c1e-9a0f-2d6b7e8c9a10/a9e4d1b2-7c3f-4e5a-8b6d-0f1e2d3c4b5a.pdf",
  "uploadUrl": "https://resumerank-resumes-<suffix>.s3.ap-south-1.amazonaws.com/resumes/...&X-Amz-Signature=...",
  "expiresIn": 300,
  "headers": { "Content-Type": "application/pdf" }
}
```

The browser then sends `PUT uploadUrl` with the file as the body and exactly the headers in
`headers`.

### `GET /candidates?jobId={jobId}`

Response `200` (already sorted by score, highest first):

```json
{
  "jobId": "3f1c2a7e-5b8d-4c1e-9a0f-2d6b7e8c9a10",
  "job": {
    "title": "Cloud Engineer Intern",
    "requiredSkills": ["aws", "docker", "linux", "python", "sql"],
    "minYears": 0
  },
  "count": 1,
  "candidates": [
    {
      "rank": 1,
      "candidateId": "a9e4d1b2-7c3f-4e5a-8b6d-0f1e2d3c4b5a",
      "name": "Test Candidate One",
      "status": "SCORED",
      "score": 96,
      "skillScore": 60,
      "expScore": 20,
      "eduScore": 20,
      "matchedSkills": ["aws", "docker", "linux", "python", "sql"],
      "missingSkills": [],
      "yearsExperience": 3,
      "textPreview": "TEST CANDIDATE ONE  Cloud Engineer ...",
      "processedAt": "2026-10-13T09:16:40Z",
      "failureReason": null
    }
  ]
}
```

Each candidate also carries `email`, `createdAt`, `decision` (`NONE` when unset) and
`decidedAt`. The route is recruiter-only, so the email can be returned.

### `GET /jobs` and `GET /jobs?jobId=`

```json
{ "count": 2, "totalCandidates": 7,
  "jobs": [ { "jobId": "…", "title": "Cloud Engineer Intern", "requiredSkills": ["aws", "python"],
              "minYears": 2, "createdAt": "2026-10-14T05:00:00Z", "candidateCount": 5 } ] }
```

With `?jobId=` the single job is returned (`title`, `requiredSkills`, `minYears`, `description`,
`createdAt`). `recruiterEmail` is never returned by this public route.

### `GET /status?jobId=&candidateId=`

The candidate's `status`, `score` (null until SCORED), component scores, `matchedSkills`,
`missingSkills`, `failureReason`, `submittedAt`, `processedAt` and the job's title and skills.
The recruiter's `decision` and the email are not returned.

### `POST /skills/extract`

Request `{ "text": "<job description, ≤ 20,000 characters>" }` → `{ "skills": ["python", "aws"], "count": 2 }`,
canonical names from `skills.json`, first-mentioned first.

### `POST /decision`

Request `{ "jobId": "…", "candidateId": "…", "decision": "SHORTLISTED" }` (or `REJECTED`, `NONE`)
→ `200` with the same fields; `404` if the candidate does not exist.

### `GET /resume-url?jobId=&candidateId=`

`{ "url": "https://…s3…/resumes/…pdf?X-Amz-…", "expiresIn": 300 }` – opens inline in the browser.
`404` once the file has expired (7-day lifecycle rule).

### How the pages find the job

`index.html` and `upload.html` list jobs from `GET /jobs`; `recruiter.html` shows a share link
`upload.html?jobId=<jobId>`; after uploading, the candidate gets
`status.html?jobId=<jobId>&candidateId=<candidateId>`.

## 4. CORS (known-good configuration, written in advance)

**API Gateway (HTTP API → CORS):**

| Setting | Value |
| --- | --- |
| Access-Control-Allow-Origin | `http://resumerank-site-<suffix>.s3-website.ap-south-1.amazonaws.com` |
| Access-Control-Allow-Methods | `GET, POST, PUT, OPTIONS` |
| Access-Control-Allow-Headers | `content-type`, `x-recruiter-key` |
| Access-Control-Max-Age | `300` |

**Resumes bucket (Permissions → CORS):**

```json
[
  {
    "AllowedOrigins": ["http://resumerank-site-<suffix>.s3-website.ap-south-1.amazonaws.com"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["content-type"],
    "MaxAgeSeconds": 300
  }
]
```

During local testing (`http://localhost:8000`) that origin may be added temporarily and
must be removed before the demo.

## 5. SNS alert

`process_resume` publishes to `SNS_TOPIC_ARN` when `score >= SCORE_THRESHOLD` (75).
Subject: `ResumeRank: <name> scored <score> for <job title>`. Body lists candidate name,
email, score, component scores and matched / missing skills.

> Note: an SNS topic delivers to **all** confirmed subscribers, so `recruiterEmail` on the
> job is informational in this prototype (the topic's subscriptions decide who is emailed).
> Per-job routing would need a subscription filter policy – listed as future work.
