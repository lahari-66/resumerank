# 3. System Architecture and Data Flow

ResumeRank is built from managed AWS services only. No virtual machine, container cluster or
database server is provisioned; every component is invoked per request or per event and costs
nothing while idle. The system has two paths that share one database:

- the **request path** – browser → API Gateway → Lambda `api_handler` → DynamoDB – used by every
  page load, form submission and leaderboard refresh, and
- the **event path** – S3 → SQS → Lambda `process_resume` → text extraction → DynamoDB → SNS –
  run exactly once for every uploaded resume.

## 3.1 Stage-by-stage flow

| # | Stage | What happens |
| --- | --- | --- |
| 1 | Load pages | The browser downloads the static pages (`index`, `recruiter`, `upload`, `status`) from the S3 website bucket. |
| 2–3 | API call | The page calls the HTTP API with `fetch()`. API Gateway checks CORS and throttling limits and invokes `api_handler`. |
| 4 | Job and candidate data | `api_handler` reads and writes the `Jobs` and `Candidates` tables: creating jobs, issuing upload URLs, serving the ranked leaderboard and recording recruiter decisions. |
| 5 | Upload | For an application, `api_handler` writes a `PENDING` candidate item and returns a pre-signed S3 PUT URL valid for 300 s and bound to `application/pdf` and the exact file size. The browser uploads the PDF straight to the private resumes bucket. |
| 6 | Queue | S3 emits an `ObjectCreated:Put` event (prefix `resumes/`, suffix `.pdf`) into the SQS queue `resumerank-queue`. |
| 7 | Process | Lambda polls the queue and runs `process_resume` – one copy per message, up to five in parallel. |
| 8 | Extract | The processor obtains the resume text (Textract OCR, or the PDF text layer – see §7) and, where available, key phrases and DATE / ORGANIZATION / TITLE entities from Comprehend. |
| 9 | Score and store | `scoring.py` computes the 0–100 score and its components; the candidate item is updated to `SCORED` (or `FAILED` with a reason) using `UpdateItem`. A custom CloudWatch metric `ResumeRank/CandidateScore` is emitted. |
| 10 | Alert | If the score is 75 or more, the processor publishes to the SNS topic and the recruiter receives an email naming the candidate, score and matched skills. |

The recruiter dashboard refreshes the leaderboard every five seconds, so a new candidate appears
within seconds of the upload without any server push.

## 3.2 Why this shape

| Design choice | Reason |
| --- | --- |
| S3 event → **SQS** → Lambda instead of S3 → Lambda directly | The queue absorbs bursts, lets Lambda scale out at a controlled rate, retries only transient failures and moves poison messages to a dead-letter queue (§9). |
| Browser uploads **directly to S3** with a pre-signed URL | No file passes through Lambda or API Gateway (which limit payload size); no AWS credential ever reaches the browser. |
| **Asynchronous** processing | The candidate gets an immediate answer; text extraction may take seconds and never blocks the API. |
| One Lambda with sequential stages instead of Step Functions | Fewer services to configure in two days; each stage is still logged separately in CloudWatch. Step Functions is listed as future work. |
| `UpdateItem` keyed on `jobId` + `candidateId` | Re-processing the same upload is idempotent and never erases the name or email written by the API. |

## 3.3 Data model (DynamoDB)

Two tables in on-demand capacity mode.

**Jobs** – partition key `jobId` (UUID).

| Attribute | Type | Meaning |
| --- | --- | --- |
| `jobId` | String | UUID generated by `api_handler` |
| `title` | String | e.g. "Cloud Engineer Intern" |
| `requiredSkills` | String set | lower-case canonical skill names |
| `minYears` | Number | minimum experience (0 for fresher roles) |
| `recruiterEmail` | String | recruiter contact |
| `description` | String | optional job description text |
| `createdAt` | String | ISO-8601 timestamp |

**Candidates** – partition key `jobId`, sort key `candidateId`, so "all candidates of one job" is a
single `Query`.

| Attribute | Type | Meaning |
| --- | --- | --- |
| `name`, `email` | String | from the application form |
| `status` | String | `PENDING` → `SCORED` or `FAILED` |
| `score` | Number | 0–100; sort key of the GSI |
| `skillScore`, `expScore`, `eduScore` | Number | the three components, stored for explainability |
| `matchedSkills`, `missingSkills` | List | shown to recruiter and candidate |
| `yearsExperience` | Number | estimate, capped at 15 |
| `textPreview` | String | first 300 characters of the extracted text |
| `failureReason` | String | why a resume could not be processed |
| `decision`, `decidedAt` | String | recruiter's `SHORTLISTED` / `REJECTED` and when |
| `s3Key`, `createdAt`, `processedAt` | String | traceability |

**Global secondary index `ScoreIndex`** – partition key `jobId`, sort key `score` (Number),
projection ALL. The leaderboard is one `Query` with `ScanIndexForward = false`, which returns the
candidates already sorted from highest to lowest score – no table scan and no sorting in code.
Because a GSI only contains items that have its sort key, the API writes `score = 0` on the
`PENDING` item; pending and failed candidates therefore still appear (at the bottom) and the
interface shows "–" instead of a number until a resume is scored.
